# AI-журнал

## ЛР6 — AI #1 (анализ: матрица прав и переходы статусов)

1. **Задача:** получить черновик матрицы «роль × действие» и переходов статусов для проверки перед реализацией сервисного слоя.
2. **Модель:** GPT-4o
3. **Промпт:** Роль: аналитик ПО. Контекст: учебная «Система учёта заявок», роли admin/operator/executor/applicant, статусы Новая/В работе/Выполнена/Закрыта, сущности Users/Requests/Categories/Statuses/Comments. Задача: матрица «роль × действие» и допустимые переходы статусов с указанием ролей. Формат: две markdown-таблицы, без кода. Ограничения: не добавлять роли и статусы, которых нет в контексте; спорные места — отдельным списком.
4. **Почему такой промпт:** задана роль аналитика, контекст (роли, статусы, сущности), формат (две markdown-таблицы) и ограничения (не добавлять лишнее) — чтобы получить структурированный ответ для сверки.
5. **Почему такая модель:** хорошо держит структурированный вывод и ограничения.
6. **Результат ИИ:** предложена матрица прав и переходов; ИИ разрешил applicant менять статус и закрывать заявку, разрешил executor создавать заявки, добавил возврат «Выполнена → В работе» и переоткрытие из «Закрыта».
7. **Проверка:** сверил(а) с ТЗ ЛР1 и с кодом `src/services/request_service.py`; прогнал(а) `pytest` — 12 passed. Расхождения с кодом зафиксированы.
8. **Собственная доработка:** отклонил(а) право applicant менять статус/закрывать (вариант 1), право executor создавать заявки, возврат и переоткрытие — как усложнение для ЛР6. Итоговая матрица — `docs/roles_matrix.md`. Тесты подтверждают выбранные правила.
9. **Вывод:** ИИ дал полезный черновик, но допустил минимум 3 расхождения с требованиями; без сверки с ТЗ и тестами использовать нельзя. Ценность — в быстром старте и списке спорных мест.

## ЛР6 — AI #2 (ревью сервисного слоя)

1. **Задача:** получить ревью `request_service.py` на нарушения слоёв, пропущенные проверки прав и edge-cases.
2. **Модель:** GPT-4o
3. **Промпт:** Роль: senior Python-разработчик и ревьюер. Контекст: учебный проект «Система учёта заявок», слоистая архитектура (repositories → services). Задача: провести код-ревью на SQL в сервисе, проверки прав, edge-cases, корректность исключений, 3–5 улучшений. Формат: замечания с пометками «критично/желательно/необязательно». Ограничения: не менять архитектуру, не добавлять роли/статусы, правила — вариант 1.
4. **Почему такой промпт:** задана роль, контекст, критерии и формат с приоритетами — чтобы получить структурированный чек-лист, а не общие слова.
5. **Почему такая модель:** хорошо анализирует код и находит edge-cases.
6. **Результат ИИ:** ИИ дал общее ревью «по типовому коду» (фактический код в промпт не попал). Замечания: проверка прав в комментариях, повторное назначение, валидация id, ConflictError для недопустимых переходов, иерархия исключений, SQL в сервисе.
7. **Проверка:** сверил(а) каждое замечание с фактическим кодом. Часть замечаний (SQL в сервисе, ORM-сессии, иерархия исключений, «executor только свои», проверка роли назначаемого) уже была реализована — отклонены как неприменимые. Прогнал(а) pytest — 12 passed.
8. **Собственная доработка:** приняты 4 замечания: проверка прав в `add_comment` (applicant — только свои, executor — только назначенные); `ConflictError` при повторном назначении; валидация `category_id` и `new_status_id`; `InvalidTransitionError` наследует `ConflictError`. Добавлены 3 теста. Исправлены тесты назначения (используют заявку 2, т.к. заявка 1 уже назначена в seed).
9. **Вывод:** ревью ИИ полезно как чек-лист, но без фактического кода половина замечаний — домыслы. Каждое замечание надо проверять по коду и тестам.

## ЛР7 — AI #1 (анализ: контракт REST API)

1. **Задача:** получить черновик контракта REST API (эндпоинты, права, коды) по Use Case и сущностям.
2. **Модель:** GPT-4o
3. **Промпт:** Роль: backend-разработчик и проектировщик API. Контекст: учебный проект «Система учёта заявок» на FastAPI, роли admin/operator/executor/applicant, сущности Users/Requests/Categories/Statuses/Comments, правила варианта 1. Задача: предложить контракт REST API (метод, путь, права, коды 200/201/400/403/404/409/422) для заявок, комментариев, справочников; как передавать пользователя. Формат: markdown-таблица + обоснование. Ограничения: без внешних auth-сервисов, не добавлять лишние сущности.
4. **Почему такой промпт:** задана роль, контекст, правила варианта 1, формат (таблица + обоснование) и ограничения (без внешних auth-сервисов) — чтобы получить проверяемый контракт.
5. **Почему такая модель:** хорошо держит структуру таблиц и HTTP-семантику.
6. **Результат ИИ:** 17 эндпоинтов, таблица кодов, `X-User-Id`, обоснование путей, спорные места помечены.
7. **Проверка:** сверил(а) с `request_service.py` и матрицей прав. Из 17 эндпоинтов реализуемы 11 (покрыты сервисом ЛР6); 6 отклонены/отложены (PATCH/DELETE заявки, CRUD категорий/статусов, POST /requests для executor).
8. **Собственная доработка:** убрал(а) создание заявки executor (противоречит варианту 1); убрал(а) PATCH/DELETE заявки и CRUD справочников как нереализованные в ЛР6; зафиксировал(а) «тихое сужение» выдачи по роли вместо 403; итоговый контракт — `docs/api_contract.md`.
9. **Вывод:** ИИ дал полный и структурированный контракт, но часть эндпоинтов выходит за объём ЛР6 — нужна сверка с фактическим сервисом, иначе API будет ссылаться на несуществующие методы.

## ЛР7 — AI #2 (ревью REST API)

1. **Задача:** получить ревью API на корректность кодов, утечки прав, единообразие ошибок и валидацию.
2. **Модель:** GPT-4o
3. **Промпт:** Роль: senior backend-разработчик и ревьюер REST API. Контекст: учебный проект на FastAPI, слои src/api → src/services → src/repositories → SQLite, аутентификация упрощённая X-User-Id, правила варианта 1. Задача: ревью на корректность HTTP-методов и кодов, утечки прав, единообразие ошибок, валидацию Pydantic, 3–5 улучшений. Формат: замечания с пометками «критично/желательно/необязательно». Ограничения: без JWT/OAuth, архитектуру не менять.
4. **Почему такой промпт:** задана роль, контекст слоёв и правил, критерии и формат с приоритетами — чтобы получить проверяемый список замечаний.
5. **Почему такая модель:** хорошо анализирует код и HTTP-семантику.
6. **Результат ИИ:** ИИ дал общее ревью «по типовому коду» (фактический код в промпт не попал). Замечания: единый формат ошибок для RequestValidationError и HTTPException, 201 на POST, 409 на конфликты, 401 на отсутствие X-User-Id, сужение выборки по роли, extra="forbid", отдельные схемы на действия, пагинация.
7. **Проверка:** сверил(а) каждое замечание с фактическим кодом. Уже было реализовано: 201 на POST, 409 при конфликтах (проверено curl), 401 при отсутствии/невалидном X-User-Id, сужение выборки по роли в GET /requests, проверка прав в сервисе комментариев, отдельные схемы StatusChange/RequestAssign. Прогнал(а) curl-сценарии — коды 200/201/401/403/409 совпадают с docs/api_contract.md.
8. **Собственная доработка:** приняты 2 замечания: extra="forbid" в схемах; вынос проверки доступа can_view в сервис. Единый формат ошибок частично — 401/403/404 отдаются как {"detail": ...}, доменные — {"error": ..., "detail": ...}; зафиксировано как известное упрощение. Отклонены: пагинация, DELETE-эндпоинты, 404 вместо 403 — вне объёма ЛР6/ЛР7.
9. **Вывод:** ревью полезно как чек-лист; без фактического кода половина замечаний — домыслы. Критично сверять каждое с кодом и прогонять curl.
